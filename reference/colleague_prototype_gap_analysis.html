Colleague's prototype vs. iData Query Agent Architecture v0.5

What the Streamlit chatbot in data_retrieving_published_rl already does, measured step by step against the architecture in reference/architecture.html, and what is still missing.

0Summary

The colleague's prototype already covers most of the runtime shell: a working chat UI, the IMF OpenAI gateway with sign-in, a bounded tool-calling loop, and iData tools for discovery, dimension inspection, value search, country-group expansion, availability probe and fetch. The fetch tool builds the key in the database's own dimension order and refuses codes that were not returned by a search tool, which is the same safety idea as our verified query sheet.

What it does not have is the "query sheet" discipline of our design: there is no QuerySpec object, no confirmation gate in code, no Python / Stata / R code generation, no structured ask_user, no local codebook cache or lookup table, and the file is offered as a browser download instead of being written to Downloads with a sidecar. It also defaults to WEO Live, which conflicts with our decision that the database is never inferred.

7What the prototype has beyond the architecture

Extra Multi-source research

IMF SDMX, DataMapper, OECD, BIS, FRED, US Treasury, each with discover → inspect → resolve → fetch tools, plus combine_retrieved_data for one long CSV across sources.

Extra Review & hand-off

Each retrieval becomes a dataset with coverage warnings (missing periods, duplicates); the user acknowledges and freezes a selection under handoffs/, downloadable as ZIP.

Extra Format agent

A second model (formatting_agent.py) that filters, pivots and builds Excel workbooks from handed-off data, without fetching or aggregating.

Extra Workbench

User-triggered Python / PowerShell / Bash runners with timeouts. Effectively our phase-3 executor, gated by a human click.

Extra Vintage guard

Frozen WEO_LIVE_* vintages are rejected unless explicitly requested. Worth adopting in our idata_find_databases.

Extra Gateway sign-in

MSAL interactive sign-in with a local token cache; this is the piece our handoff assumed the harness would provide.

8How the two pieces fit, and what is left

The prototype is, in effect, the "harness side" our idata_agent/handoff/README.md describes: model loop, dispatch, UI, sign-in. Our repository holds the other half: QuerySpec, the nine tool implementations with caching and the lookup table, codegen, and the skill text. Merging them closes most gaps.

Take from the colleague as is

  • Streamlit UI, the gateway client (imf_openai_helper.py) and the loop in run_openai_agent.
  • idata_client.enrich_data / validate_key logic and the vintage guard.
  • code_runner.run_python as the base for running idata_fetch in a child process.

Plug in from our side

  1. Tools: route the iData tool names to idata_agent.tools.implementation(name), with schemas from to_openai_tools(). Gives fuzzy database match, cached codebooks, top-5 indicator search with lookup boost, and render_code.
  2. QuerySpec in session state: keep one sheet per conversation in st.session_state so follow-up edits do not re-resolve everything.
  3. Confirm gate in code: render the sheet + three code tabs; only the Confirm button sets stage = "confirmed"; idata_fetch refuses otherwise.
  4. idata_fetch: from handoff/executor_reference.py, run in a child process, write to Downloads with sidecar.
  5. ask_user: intercept in the loop and render as option buttons.
  6. System prompt: use SKILL.md for the iData part; keep the colleague's OECD / BIS / SDMX rules for the other sources.
  7. Logging: append confirmed indicator picks to knowledge/lookup_review.jsonl.

Decide with the colleague:

  • Default database. The prototype starts with WEO Live; our design asks. Options: keep asking, or show WEO Live as a pre-selected first candidate that the user still confirms.
  • Confirm before vs. after fetch. His Review & hand-off confirms the result; ours confirms the query. They can coexist, but the pre-fetch gate is what stops wrong codes being downloaded.
  • Scope. Our architecture is iData-only. Decide whether the other sources stay in v1 or are kept behind a switch.
