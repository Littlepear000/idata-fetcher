Finding the right indicator across all iData databases

The economist's principle: the user should do as little as possible. So the agent, not the user, picks the database. From one sentence it returns the top 3–5 indicators, each with its database and official description, and the user confirms once.

Recommendation in one line: yes, build one combined indicator file, but treat it as a search index the program queries, not a file the AI reads. Build it offline from a curated list of databases. At query time, ordinary code narrows it to about 30 candidates, the AI re-ranks them to a top 5, and the user confirms with one click.

1Why an index is needed

  • imf_datatools has no cross-database indicator search. get_databases(keyword=…) only matches database names and descriptions; get_dimension_values(db, dim, keyword=…) searches one database at a time, by substring.
  • Its caching is in-memory, per session. Every new session would have to call every database again.
  • A database description rarely lists the indicators inside it, so "pick the database first by its description" misses a lot.

So to answer "which database has real GDP growth?" without asking the user, we need our own list of every (database, indicator) pair.

3Recommended design

Build time: the indicator index

A script run by the team; refresh monthly, plus a manual button

  1. codeget_databases(), then apply a curated list of in-scope databases. Drop frozen vintages (WEO_LIVE_2025…) and duplicates; give each kept database a priority (e.g. WEO Live above derived products).
  2. codeFor each database: get_dimensions(), find the measure dimension(s) (INDICATOR, or for CPI-style databases INDEX_TYPE, COICOP_1999, …).
  3. codeget_dimension_values() on those dimensions only. Index each dimension's values separately, not every combination, so the file does not explode.
  4. codeSave one row per value: database, database name, priority, dimension, code, description, unit (if known). A local SQLite file with full-text search is enough; country and frequency lists stay per-database, as now.

Query time: from words to top 5

Each user request; takes seconds, no iData calls until the preview

  1. AITurns the user's words into 2–3 English search phrases and hints (rate vs. level, real vs. nominal, % of GDP…). It writes words, never codes.
  2. codeSearches the index: word match + fuzzy match + abbreviation table + lookup-table boost + database priority. Keeps the top ~30.
  3. AIRe-ranks those 30 by reading the descriptions against the request and picks 5. It can only choose from the list.
  4. codeOptional: a tiny preview fetch for the top candidates, to drop ones with no data for the requested countries.
  5. userSees the top 5 and confirms one (or rephrases). The pick is logged to grow the lookup table.

Handling the hard cases

  • Same concept in several databases. Database priority decides the default (the economist supplies the ranking); the others appear lower in the list with their source shown.
  • Composite measures (CPI-style). The index finds the database and the main measure value; the remaining measure dimensions (transformation, index type) are then resolved inside that database, as in the current design.
  • Synonyms the word match misses ("inflation" vs. "consumer prices"). Covered first by the AI writing several search phrases and by the abbreviation and lookup tables. If tests still show misses, add embedding search as one more score term, if the IMF gateway offers an embedding model.
  • Access differs by user. The index may list databases a given user cannot open. The preview step catches this and the candidate is dropped or flagged.

4What this changes in the current architecture

  • Database step: v0.5 says "never infer the database, ask the user". This proposal reverses it: the agent infers the database and the user confirms it together with the indicator, in one step.
  • Tools: a new idata_search_indicators(phrases, hints) searches across databases and replaces the "find database, then search values" pair for the indicator. idata_find_databases stays for users who name a database.
  • Knowledge files: new indicator_index.sqlite, database scope and priority list, and a build script. The existing per-database cache and lookup table are reused.

To settle before building

  1. Size: how many databases and indicators are actually accessible? A one-off census script (count only) answers this in one run on an IMF machine.
  2. Scope and priority: which databases are in scope for v1, and in what order of preference? This needs the economist.
  3. Embeddings: does the IMF gateway offer an embedding model? This is not needed for v1, but useful to know.
  4. Refresh: who runs the index build, and how often? Monthly is suggested, WEO Live around each round.
