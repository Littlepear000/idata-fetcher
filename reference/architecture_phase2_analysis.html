iData Agent — Phase 2: Analysis

The user works in a working directory that holds their data, for example the files downloaded in Phase 1. They either pick a ready-made common function (trend, forecast error, …) or describe what they need. The agent writes the code in Stata, R or Python, the user reviews it and clicks Run, and the program runs it on the user's computer and writes the results into the working directory.

← Phase 1 · Data RetrievalPhase 2 · Analysis

★What changed since v0.6

Generated code is the main path

v0.6 planned one fixed tool per analysis ("recipes") and left free-form code for later. Now the AI writes code for any request, the way Claude Code does, and a person reviews it before it runs. Needs vary too much to define a tool for each.

Common functions as a shortcut

Frequent analyses (trend, forecast error, group aggregate, …) are a catalog shown first. Each is reviewed and tested once by the team; the user fills a short form instead of describing it. Section 3.

Three languages, all runnable

The user chooses Stata, R or Python, and the chosen code runs on their own computer, provided that language is installed. Section 5.

0Two examples

With a common function

User: opens Analysis, sees the catalog, picks Forecast error.

Form: data file WEO_vintages_G7_NGDP_RPCH.csv (from the working directory), target years 2015–2024, horizon "year ahead", actual = current WEO Live, error = actual − forecast. Language: Python.

Result: the code appears, the user reviews and clicks Run; an error table, bias / MAE / RMSE by country and a chart land in the working directory.

With a description

User: "None of these. For each country in my file, compute the average primary balance in years when growth was below 1%, and compare with other years." Language: Stata.

Agent: looks at the file's columns and a few rows, writes a do-file, explains it in three lines.

Result: the user reviews and clicks Run; Stata runs in batch mode; the table and the log land in the working directory. A typo in a variable name? The agent reads the error, proposes a fix, the user reviews again.

3Common functions

A common function is an analysis the team has written, reviewed with an economist and tested once, so users get it right without describing it. It replaces the v0.6 "recipe" tools, but it is a shortcut in the interface, not a tool the AI must call.

What each common function contains

  • Name, version, one-line description for the catalog
  • Parameters with types and defaults; the form is generated from them
  • Expected input: which columns it needs, with automatic matching for Phase 1 files
  • Code template per language; the catalog shows which languages exist (Python first)
  • Method note: definitions, defaults and pitfalls, also read by the AI in path B
  • Test case: a small input and the expected output, run for every language version

4Path B: the AI writes the code

This works like Claude Code: the model writes code as a tool call, the program runs it, and the result goes back to the model. Two differences make it fit IMF machines: the model has no tool that runs code, and the result goes back only after the user approved the run.

The AI's tools in Phase 2

ToolPurposeWhat the AI gets back
list_workdir_filesFiles in the working directory (data types only: csv, xlsx, dta, parquet, txt)names, sizes, dates
inspect_fileUnderstand one data file before writing code for itcolumn names and types, 5 rows, row count, countries and period covered; reads the sidecar if it is a Phase 1 file
read_method_noteDefinitions and pitfalls for a topic (forecast errors, aggregation, trends, …)the note's text
suggest_common_functionPoint the user to a catalog entry that fits the requestshows the form, pre-filled
propose_codePut code on the review screennothing until the user acts; after a run: exit status, end of the log, files written, short previews
ask_userOne question with options when the request is ambiguousthe user's answer

All file tools take a file name inside the working directory, never a path, and only previews go to the model; full data stays on the computer.

Rules given to the AI

  • Read the files with inspect_file before writing code that uses them; do not guess column names.
  • Read the method note when the request touches a topic that has one, and follow its definitions; state any choice the note leaves open in the explanation.
  • Read inputs from the working directory, write outputs only into the run folder, and list the outputs in propose_code.
  • Do not download data in the analysis code. If data is missing, say so and offer to go to Phase 1 (section 6).
  • Keep code plain: standard packages only (pandas, numpy, statsmodels, matplotlib; base R + common packages; Stata built-ins), with comments on each step.
  • When a common function fits, suggest it instead of writing new code.

  • Finding the programs. At start-up the program looks for Python (always present), Rscript.exe and the Stata executable in their usual install folders; the user can set the paths in settings. Languages not found are greyed out on the language choice.
  • Child process, no shell. The program is started directly with a list of arguments (subprocess.run(..., shell=False)), with the run folder as working directory, a reduced set of environment variables and a time limit (default 10 minutes, adjustable). The interface stays responsive and can stop the run.
  • One run, one folder. Each run writes to its own folder, so nothing is overwritten and every result can be traced:

Re-running script.py by hand gives the same results, so the user can take it into their own work without the agent.

6Safety and data rules

Running AI-written code on an IMF computer is the main risk of Phase 2. Claude Code and Codex are not allowed on IMF PCs, partly for this reason. Windows offers no simple sandbox here (no Docker), so the protection is layered, with a person approving every run. This design should be reviewed with IT before Phase 2 is built.

LayerWhat it does
Human approvalNothing runs without the user's Run click on the review screen, including fixes after an error. The AI has no tool that runs code.
Checks before runningPython: the code is parsed and blocked if it imports or calls things like subprocess, os.system, shutil.rmtree, file deletion, network libraries (requests, urllib, socket), eval/exec. Stata and R: pattern rules block shell/!, erase/rm, system(), unlink(), download.file() and similar. Any write outside the run folder is flagged. Blocked code shows the reason on the review screen.
RunningNo shell; run folder as working directory; reduced environment; time limit; stop button.
After runningThe program lists every file changed in the working directory. Anything outside the run folder is reported to the user.
Data to the modelOnly column names, a few rows, counts, and the end of logs. Full data never leaves the computer.
Data retrievalAnalysis code does not call imf_datatools or idatause; the checks flag it. Data comes from Phase 1, where the confirmation and vintage rules apply. The agent offers "Get this data in Phase 1" when something is missing.

The checks catch mistakes and obvious misuse; they cannot stop all harmful code. That is why the review step stays, and why the code is shown in full rather than summarised.

7How Phase 1 and Phase 2 connect

  • Same folder. The working directory defaults to the Phase 1 download folder.
  • Known files. Phase 1 files have standard columns and a sidecar .json, so inspect_file can tell the AI the database, indicator, unit and scale, and common-function forms can fill in columns automatically.
  • Missing data. If an analysis needs data that is not in the folder (e.g. weights for an aggregate), the agent says what is missing and opens the Phase 1 flow with a drafted request; after the download it returns to the analysis.
  • Other files. Files the user put in the folder themselves work too; the AI inspects them the same way, without a sidecar.

8Open questions

  1. IT approval. Will IT accept a local app that runs AI-written code after the user's review, with the checks above? This decides whether Phase 2 can be built as designed.
  2. Stata and R on IMF PCs. Which versions are installed, where, and does the Stata licence allow batch mode started from another program?
  3. First common functions. Which analyses do economists ask for most often, and what are their default method choices? (The six in section 3 are a starting list.)
  4. Code quality per language. How well does the gateway model write Stata and R compared with Python? To be tested with a set of sample requests in each language before release.
  5. Editing code. Should users be able to edit code directly on the review screen, or only ask the AI for changes? Direct editing is assumed; the edited version is what gets saved.
