iData Query Agent Architecture

A chat agent that turns a plain-language data request into a verified imf_datatools query, shows the equivalent Python, Stata and R code, runs it, and drops the result in the user's Downloads folder.

1Goal and scope

The user types something like "real GDP growth for the US and Japan since 2015 from WEO". The agent must end with a file on disk and, along the way, show exactly which database, dimension codes and time range it used, in code the user can paste into their own Python, Stata or R session.

Everything the agent produces is governed by one package, imf_datatools, whose iData interface is small: five discovery and retrieval functions, a dot-separated query key, and the same key syntax across Python (get_idata_data), Stata (idatause data, query()) and R (reticulate calling the Python module). That is what makes a deterministic design possible. The hard, fuzzy work is deciding what to put in the key. Writing the code once the key is known is mechanical.

In scope for v1

  • iData databases only (WEO_LIVE, WEO, CPI, IFS, GFS, BOP, IMTS, and whatever get_databases() returns).
  • One query per request. Several countries and several indicators in that query are fine.
  • Output as wide or long CSV, or Excel, saved to a default folder.
  • Code shown in all three languages. Execution happens in Python only.

Deliberately out of v1

  • Haver, DMXe, SQL, World Bank sources. Tool names are prefixed idata_ so these can be added later without renaming.
  • Post-processing (growth rates, frequency conversion, merges). This is where free-form LLM code generation would be needed, and it is a separate phase.
  • Running Stata or R itself. Users copy that code into their own session.

2System overview

Five layers. The front end and the LLM provider sit at the two edges and are the two things most likely to change, so each talks to the core through a thin adapter. The core owns the conversation state and decides which tool to call next. Tools are plain Python functions that wrap imf_datatools, and they are the only code that touches iData.

3The QuerySpec contract

Everything in the agent revolves around one structured object. The parse step fills it with plain-language slots, the resolve step replaces each slot with verified codes, the confirm step shows it to the user, codegen renders it, and execute runs it. If a later turn says "actually make that quarterly", only the spec changes and the pipeline re-runs from the resolve stage.

First sketchFour fixed fields

database, country, year, indicator[]

Matches WEO_LIVE (COUNTRY.INDICATOR.FREQUENCY) but not CPI, which has five dimensions in a different order, or IMTS, which has a counterpart-country dimension. The key would need per-database special cases.

ProposedDimension-generic spec

database + an ordered list of dimensions[] read from get_dimensions(db) at runtime, each with its resolved values, plus time range, layout and language.

The four fields still exist as the user-facing summary. Internally they are just the most common dimensions. Any database the package returns works without new code.

{
  "database":   "IMF.RES.WEO:WEO_LIVE",
  "dimensions": [                                   // order comes from get_dimensions(db)
    {"name": "COUNTRY",   "values": ["USA", "JPN"],  "from": "the US and Japan"},
    {"name": "INDICATOR", "values": ["NGDP_RPCH"],   "from": "real GDP growth"},
    {"name": "FREQUENCY", "values": ["A"],           "from": "(only one value: auto-resolved)"}
  ],
  "key":   "USA+JPN.NGDP_RPCH.A",                    // derived, never typed by the LLM
  "start": "2015", "end": "2026",
  "layout": "wide", "file_format": "csv",
  "language": "python",
  "output_path": "~/Downloads/WEO_LIVE_USA+JPN_NGDP_RPCH_A_2015-2026.csv",
  "stage": "confirmed"                               // parsed → resolving → confirmed → executed
}

Two rules make the spec trustworthy:

  • The LLM never writes the key. The dispatcher derives it from dimensions[], so the segment count always matches the dimension count and the order is always right.
  • Every value carries a from. The original phrase the user wrote is kept beside the code it resolved to, so the confirm screen can say "real GDP growth → NGDP_RPCH (Gross domestic product, constant prices, percent change)".

4Request lifecycle

The conversation is a state machine, not a free agent loop. The LLM drives within each stage, but the dispatcher refuses tool calls that skip a stage: idata_fetch is rejected unless every dimension in the spec is resolved and the spec is confirmed. That is enforced in code, not only in the prompt, which is what makes the behaviour reliable across models.

5Tool catalogue

Nine tools. Five wrap one imf_datatools function each and already exist as schemas in skills/imf-idata-python/archive/tool_schemas.py. The remaining four are new and small. Every tool returns the same envelope, {ok, data} or {ok:false, error:{type, message}}, so the agent loop never crashes on a bad call.

Why no run_python / run_shell tool in v1. The gateway test showed generic code execution works, but a generic executor means the model can write anything, and the key-building mistakes we most want to prevent (wrong dimension order, guessed indicator codes) become possible again. idata_fetch is a fixed program with a validated input. A general run_python is the right tool for phase 3 post-processing, and the executor design (python subprocess, no bash) carries over unchanged.

6Indicator resolution

This is the step the first sketch correctly identified as the hard one. get_dimension_values(db, 'INDICATOR', keyword=…) is a case-insensitive substring match on code and description. "real GDP growth" does not match "Gross domestic product, constant prices, percent change", and WEO_LIVE has several hundred indicators. So the tool behind idata_search_values is a three-tier funnel, and the raw package call is only the first data source.

The codebook cache

Tier B needs the complete value list for a dimension, not a server-side substring filter. On first use of a database the tool pulls get_dimension_values(db, dim) for every dimension and writes it to a local JSON file keyed by database and dimension with a fetch timestamp. Subsequent calls read the file. A refresh happens when the file is older than a configurable age (one day is a sensible default) or when the user asks. WEO_LIVE's indicator list is a few hundred rows; CPI's COUNTRY list is about 200. These are small files.

The same cache feeds the confirm screen (code → description lookup without another API call) and the evaluation suite (tests run offline against a frozen snapshot).

The alias table

A YAML file the team curates, one block per database: "gdp growth" → NGDP_RPCH, "inflation" → PCPIPCH, "current account" → BCA. It encodes exactly the knowledge an experienced desk economist has and the package does not. Every confirmed user pick is appended to a review file so the table grows from real use. This is also the natural home for IMF-specific conventions such as "fiscal balance usually means GGXCNL_NGDP unless primary is mentioned".

Countries and time

Countries are easier: ISO3 is the index in every database, country names come from the same cache, and groups come from idata_expand_group. Time is a pair of strings in the package's own formats (2020, 2020Q2, 2020-05) and the parse step normalises relative phrases such as "last ten years" against today's date. Frequency is a dimension like any other, with one twist: if the user does not say and the database offers several, the agent asks rather than defaulting to annual.

7Code generation

Once the spec is resolved, the three language versions are a template render, not a model call. The package deliberately uses one key syntax everywhere, so the only differences are language boilerplate. Here is the same spec in all three outputs, as the templates would produce it.

Python (this one is executed)

from imf_datatools import idata_utilities
idata_utilities.PRIVATE = True   # internal databases

db  = 'IMF.RES.WEO:WEO_LIVE'
key = 'USA+JPN.NGDP_RPCH.A'      # COUNTRY.INDICATOR.FREQUENCY
df  = idata_utilities.get_idata_data(
        db, key=key, start='2015', end='2026')

df.to_csv(r'C:\Users\<you>\Downloads\WEO_LIVE_USA+JPN_NGDP_RPCH_A_2015-2026.csv')

Stata

* one-time: installdatatools, dev
idatause private
idatause data, ///
    database(IMF.RES.WEO:WEO_LIVE) ///
    query(USA+JPN.NGDP_RPCH.A) ///
    tin(2015, 2026) clear

export delimited using ///
    "C:\Users\<you>\Downloads\WEO_LIVE_USA+JPN_NGDP_RPCH_A_2015-2026.csv", replace

R

library(reticulate)
use_python("C:/ProgramData/Python3", required = TRUE)
Sys.setenv(TZ = "UTC")   # reticulate date shift, see doc §5.1
imf_datatools <- import("imf_datatools")
imf_datatools$idata_utilities$PRIVATE <- TRUE

df <- imf_datatools$get_idata_data(
        'IMF.RES.WEO:WEO_LIVE', 'USA+JPN.NGDP_RPCH.A',
        start = '2015', end = '2026')

write.csv(df, "C:/Users/<you>/Downloads/WEO_LIVE_USA+JPN_NGDP_RPCH_A_2015-2026.csv")

Template inputs beyond the spec: layout selects longformat=True / panel() variants, file_format selects the save line (CSV, Excel, and in Stata a native save .dta), and a comment line above the key spells out the dimension order so the code is self-explaining when pasted elsewhere.

Why templates and not the model. A template cannot drop a dot from the key, invent a parameter, or forget PRIVATE = True. It makes the three languages free once the spec is right, it makes the code testable with ordinary unit tests, and it guarantees the code the user copies is the code that produced the file. Free-form generation is kept for phase 3, where the request includes transformations the package has no single call for.

8Execution and delivery

idata_fetch is fetch_idata.py turned into a function: it validates the spec, calls get_idata_data, attaches scale and unit from get_idata_metadata, writes the file, and returns a JSON summary. Three points matter for the desktop setting:

  • Subprocess, not in-process. The first private-data call opens a browser tab for SSO and blocks until the user clicks through. Running the fetch in a child process with the company interpreter keeps the UI responsive and lets the core emit a "waiting for IMF sign-in" event. The one-hour session expiry is a known failure mode, and the error mapping turns the package's exception into a plain "sign in again" message.
  • Windows has no bash. The executor spawns C:\ProgramData\Python3\python.exe directly with arguments; no shell is involved. The same executor can later run a user-approved PowerShell line if that is ever needed.
  • Output location and name. Default folder is the user's Downloads (overridable in settings). File name is derived from the spec, {DB}_{COUNTRY}_{INDICATOR}_{FREQ}_{start}-{end}.{ext}, truncated with a hash if a many-country key makes it too long. A sidecar .json with the spec and the retrieval trace sits beside it so a file found later can be re-run.

The deliver stage shows the path, row and column counts, the first five rows, scale and unit, and the retrieval path (database searched, dimensions read, values matched, preview result). That last item is what the Streamlit prototype already shows, and it is the thing that lets a user trust a number without reading code.

9Swappable front end

The team's conclusion was to prototype in Streamlit and ship with pywebview plus an HTML page, and to make the swap cheap. The way to make it cheap is to give the core no opinion about the UI at all: one entry point, one event stream. This is the shape of Codex too, where the agent core and the protocol crate know nothing about the terminal UI that renders them.

Practical consequences:

  • Streamlit's rerun-everything model is contained: the session object lives in st.session_state and only new events are rendered. The tool-call cost the team worried about is paid once, inside the session, not per rerun.
  • The confirm screen is an ask_user event with structured options, so Streamlit renders buttons and the HTML page renders a form, from the same data.
  • A third adapter, a plain CLI that prints events, is nearly free and is what the evaluation suite uses.

10LLM and provider layer

The gateway test confirmed that the IMF API key generates tool calls for custom tools. That settles the main question: a custom harness is viable, so the archived harness design is the right starting point. Two adapter concerns stay isolated from the core:

  • Envelope shape. Anthropic's tool_use blocks and OpenAI's tool_calls array differ in shape. The adapter converts both to one internal ModelTurn(text, tool_calls[]) and converts tool results back. archive/test_harness.py already contains both conversions.
  • Schema dialect. Tool schemas are written once in JSON Schema and wrapped per provider (input_schema vs parameters). Keep the source in one file.

Model usage is small and bounded: one structured-output parse call, a handful of tool-calling turns during resolve, one re-rank call per ambiguous dimension, and a short natural-language summary at the end. There is no model call in generate, execute or deliver. A session should typically cost under ten model calls, which also makes the gateway's rate limits a non-issue.

The system prompt is the ruleset in SKILL.md rewritten for a harness rather than for Claude Code: it loses the Bash invocation details and keeps the discovery order, the ask-vs-auto rules and the troubleshooting guidance. Tool descriptions restate the rule that matters for that tool, because descriptions stay in context even when the prompt scrolls.

12Changes from the first sketch

The original idea (parse four fields, look up indicators via metadata, generate code in three languages, execute via tools, save to Downloads) survives intact. These are the places where this design departs from it, and why.

  1. Four fields become a dimension-generic spec. Databases differ in dimension count and order. Reading them at runtime removes a whole class of key-building bugs and makes new databases free.
  2. Understanding and syntax are separated. The model fills a schema; templates write the code. The first sketch had the model generate code directly, which makes the three languages three chances to be wrong.
  3. Execution is Python only, whichever language the user chose to view. Stata and R code are for copying. This avoids needing Stata licensing or an R install in the agent's environment and means one executor to harden.
  4. The stage order is enforced in the dispatcher, not only asked for in the prompt. A fetch without resolved dimensions is rejected with a message the model can act on.
  5. Indicator lookup is a funnel, not a single metadata call. Substring search alone will miss most natural phrasings. Alias table plus cached codebook plus a small re-rank call gets to one answer most of the time and asks only when needed.
  6. A confirm gate sits before execution. It costs one click and prevents the most expensive failure, a wrong file that looks right.
  7. Every session leaves a trace. The retrieval path shown to the user is the same record the evaluation suite replays. Confirmed indicator picks feed the alias table.

14Roadmap and repo layout

Phase 1 · MVP
  • Core session, state machine, QuerySpec, provider adapter for the IMF gateway.
  • Nine tools, dispatcher with stage checks, local codebook cache, hand-written alias table for WEO_LIVE and CPI.
  • Templates for the three languages. Python execution in subprocess. Downloads output with sidecar.
  • Streamlit adapter. CLI adapter for evals. Twenty-case eval suite against the mock package.
  • Acceptance: every eval case produces the expected spec, and a real run on an IMF machine produces a file for WEO_LIVE and CPI.
Phase 2 · Desktop
  • pywebview adapter with the HTML page. Settings for output folder and default language.
  • Shared codebook snapshot on the datatools share. Alias review workflow.
  • Multi-query sessions: "now the same for Korea" edits the spec; "and also CPI" opens a second spec.
Phase 3 · Beyond retrieval
  • A sandboxed run_python tool for post-processing requests (growth rates, frequency conversion, merges), with the fetched file as its input and the same confirm gate.
  • Other datatools sources (Haver, DMXe, World Bank) as sibling tool families.
