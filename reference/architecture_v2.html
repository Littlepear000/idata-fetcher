iData Agent Architecture

The user describes, in one sentence, the data they want or the analysis they need. The agent finds the right indicator and database, confirms once, retrieves the data with imf_datatools, runs fixed and tested analysis functions if asked, and saves the results to the user's folder with reproducible code.

★What changed since v0.5

The agent picks the database

The user no longer names one. A local index of indicators from all in-scope databases lets the agent return the top 3–5 matches as indicator + database + description. The user confirms once. Sections 2, 3, 5.

Analysis layer

New "recipes": fixed, tested functions such as WEO forecast errors and weighted country-group aggregates. Each recipe is one tool, built from a shared template. Section 6.

User folders

The user sets an output folder (default Downloads) and may declare an input folder whose files the agent can list and read. Sections 1, 4, 7.

The previous version is kept at reference/architecture.html.

Still four parts stacked top to bottom. The toolbox now has three drawers, and a workspace sits beside the data environment.

5The hard step: from plain words to indicator + database

Principle unchanged: the databases' own indicator lists are the only source of truth. What changes is the scope: instead of one database's list, the agent searches a local index built from the lists of every in-scope database. imf_datatools has no cross-database search, and its caches last only one session, so the index is built ahead of time.

Build time

  1. Scope. get_databases() lists everything the user can see. A team-owned list keeps the in-scope databases, drops frozen vintages and duplicates, and gives each a priority (e.g. WEO Live first). Vintages stay out of the search index but remain reachable through tool ② for recipes.
  2. Measure dimensions. For each kept database, get_dimensions() tells which dimension holds the indicator (INDICATOR in WEO; INDEX_TYPE, COICOP_1999, TYPE_OF_TRANSFORMATION in CPI-style databases). Each such dimension's values are indexed separately, not every combination, so the index stays small.
  3. Write the index. One row per value: database, database name, priority, dimension, code, description, unit if known, in one local SQLite file with full-text search (Python's built-in sqlite3, nothing to install). Country and frequency lists stay in the per-database cache.
  4. Refresh monthly and after each WEO round, plus a manual button.

Query time

  1. Phrases. The AI turns the user's words, in any language, into 2–3 English search phrases plus hints (level or rate, real or nominal, local currency or USD, % of GDP).
  2. Retrieve and score, in code. A fixed SQL full-text query, with only the phrases filled in, returns a few hundred rows. Python then scores them: word overlap, string similarity, abbreviation expansion, exact-code match, lookup-table boost and database priority. The top ~30 are kept.
  3. Re-rank. The AI reads those 30 descriptions against the request and the hints, and picks five. It can only choose from the list.
  4. Confirm. Each candidate shows code, description, unit, database and frequency; the best is pre-selected. If none fit, the user rephrases or names a database.
  5. Learn. The pick is logged as "words → database + code"; the team reviews the log and promotes frequent pairs into the lookup table.

Several indicators in one request are matched and confirmed separately. If they land in the same database they share one query (NGDP_RPCH+PCPIPCH). If not, they become two query sheets and two files.

6Analysis layer: recipes new

Is each analysis a tool? Yes. Each analysis is a tool the AI calls by name, and all of them are built on one shared template, the recipe. Adding a new analysis means writing one recipe; the tool definition, the confirmation sheet, the script and the tests follow from it.

The recipe contract

What every recipe declares

  • name, version, one-paragraph method note
  • parameters, with types and defaults; the tool's argument format is generated from them
  • data plan: given the parameters, the list of query sheets it needs
  • run: a pure pandas function from datasets to results; no iData calls, no AI
  • checks: coverage rules, e.g. refuse when too many countries are missing
  • script template: the same calculation as a standalone Python script

Why recipes, not "let the AI write the analysis"

  • Correct by construction. Weighting, matching vintages to horizons, and handling missing members are where analyses go wrong. Written once, reviewed by an economist, tested on known cases.
  • Same answer every time. The same request and data give the same numbers, which a free-form script does not guarantee.
  • Data never goes through the model. Recipes work on dataset ids in the workspace; the AI sees summaries only.
  • Chainable. A recipe's result is a dataset, so another recipe can use it (e.g. forecast errors of a G7 aggregate).

Recipe 1: forecast error (analysis_forecast_error)

ItemDesign
QuestionHow far were WEO forecasts of an indicator from the outcome, by country, horizon and vintage?
Parametersindicator; countries or group; target years; vintages (default: all April and October vintages available in the range); horizon (current year, year ahead, or both)
Method choices on the sheetActual = current WEO Live (default), or first release (the value of year t in a later vintage, e.g. the April t+1 vintage). Sign = actual − forecast (default). Horizon = target year − vintage year.
Data planTool ② lists vintage databases (IMF.RES.WEO:WEO_LIVE_YYYY_MON_VINTAGE); one retrieval per vintage with the same key, plus one for the actuals. Recipes pass vintage ids explicitly, so the "no vintage by accident" guard still holds for normal retrieval.
OutputsLong table: country, target year, vintage, horizon, forecast, actual, error. Summary: mean error (bias), MAE, RMSE by country and horizon. Chart of errors over target years.
ChecksWarns when a vintage lacks a country or year; never mixes vintages from different WEO rounds into one horizon.

Recipe 2: weighted country-group aggregate (analysis_group_aggregate)

ItemDesign
QuestionA time series of an indicator for a country group, weighted by economic size.
Parametersindicator; group (expanded with tool ⑤) or a custom list; years; frequency
Method choices on the sheetWeights: GDP at PPP (PPPGDP, default for growth and inflation), GDP in USD (NGDPD), population (LP) or equal. Weight year: same year (default) or a fixed base year. Operation: weighted mean for rates and ratios; sum only for levels in a common currency. The recipe refuses to sum percentages.
Data planTwo retrievals from the same database: the indicator and the weight series, for all members and years.
Missing membersWeights are re-scaled over members with data, but only when they cover at least 90% of the group's weight in that year (editable). Otherwise that year is left empty and flagged.
Cross-checkIf the database already publishes this group's aggregate, it is shown alongside. WEO's own aggregation method may differ, so differences are reported, not "corrected".
OutputsSeries by year, member coverage share per year, chart, method note.

7Code generation and execution

For a retrieval, the three language versions are a template fill with no AI involved; imf_datatools uses the same query syntax in all three. For a recipe, the script is Python: the retrievals of the data plan followed by the calculation, written out in plain pandas so it runs without this project's package.

Python (the one the agent runs)

from imf_datatools import idata_utilities
idata_utilities.PRIVATE = True

db  = 'IMF.RES.WEO:WEO_LIVE'
key = 'USA+JPN.NGDP_RPCH.A'   # COUNTRY.INDICATOR.FREQUENCY
df  = idata_utilities.get_idata_data(
        db, key=key, start='2015', end='2026',
        longformat=True)
df.to_csv(r'<output folder>\WEO_LIVE_....csv')

Stata

idatause private

Execution

  • Only Python runs. Stata and R code is for copying.
  • In a child process. The first internal-data access opens a browser sign-in that blocks; in a child process the interface stays responsive and shows "waiting for IMF sign-in". Expired sessions (one hour) become "please sign in again". The IMF interpreter is started directly, with no shell.
  • Into the output folder. The interface sets the folder (default Downloads); the AI cannot change it. File names come from the sheet. Each file has a sidecar .json with the sheet, the analysis sheet if any, the recipe version and the retrieval trace, so a file found later can be traced and re-run.
  • Data plans run in sequence under one sign-in, with progress shown ("vintage 7 of 20"). A failed retrieval stops the recipe and is reported; partial results are not silently used.

8Open questions

  1. Index size and scope. How many databases and indicators are accessible, and which databases are in scope for v1, in what priority? (A count-only census script; the economist sets the priority.)
  2. Vintage coverage. Which WEO vintages exist in iData, and how far back? This limits the forecast-error range.
  3. Recipe defaults. The economist confirms the defaults: "actual" definition and sign for forecast errors; weights and coverage threshold for aggregates.
  4. First recipes after these two. Which analyses do economists ask for most often?
  5. Embeddings. Does the IMF gateway offer an embedding model, as an optional extra score term for indicator search?
