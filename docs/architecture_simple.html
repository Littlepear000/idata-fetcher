iData Query Agent Architecture

The user describes the data they want in one sentence. The agent turns it into a correct imf_datatools query, shows the Python / Stata / R code, runs it, and saves the file locally.

0An example first

User types

"Real GDP growth for the US and Japan since 2015, from WEO"

→

Agent returns

1. A confirmation sheet: database WEO_LIVE, countries USA + JPN, indicator NGDP_RPCH, annual, 2015–2026

2. Code in three languages, ready to copy

3. A file: ~/Downloads/WEO_LIVE_USA+JPN_NGDP_RPCH_A_2015-2026.csv

Throughout, the AI is responsible for understanding the request and finding the right codes. Ordinary code is responsible for writing the query, running it and saving the file. That split is the core of the design, and every section below follows from it.

1Overall structure: four parts

Think of the system as four parts stacked top to bottom. Each part talks only to its neighbours.

2The central object: a "query sheet"

The agent maintains one thing from start to finish: a query sheet (QuerySpec in code) that fills up step by step. The AI first drafts it with the user's own words, then uses the tools to replace each cell with a verified code. Nothing runs until the user has confirmed the sheet.

One departure from the first sketch. The first idea was four fixed fields: database, country, year, indicator. But databases differ in their "dimensions": WEO is country × indicator × frequency, three dimensions; CPI has five, in a different order. So the country / indicator / frequency rows are not hard-coded. The agent first asks the database which dimensions it has, then creates one row per dimension. Adding a new database needs no new code. The user still sees the table above.

4Toolbox: nine tools

A tool is a Python function the AI can call by name. The first five each wrap one imf_datatools function, and their definitions already exist in the repo at skills/imf-idata-python/archive/tool_schemas.py. The last four are new and small.

#ToolPurposeimf_datatools function

②idata_get_dimensionsAsk a database which dimensions it has, and in what orderget_dimensions()
③idata_search_valuesFind codes in one dimension by description (countries, indicators, frequency all use this); returns candidates ranked by relevanceget_dimension_values() full list (cached locally) + fuzzy matching; the lookup table only adds score
④idata_expand_groupExpand "advanced economies" and similar groups into a country-code listget_weo_country_groups() / get_weo_country_info()
⑤idata_get_metadataUnit, scale and methodology of a series, used to explain an indicator on the confirmation sheetget_idata_metadata()
⑥idata_previewFetch only the first few rows to confirm the query really returns dataget_idata_data() (head only)
⑦render_codeFill the sheet into templates for the three languages. No AI involvedcode templates

Why v1 does not give the AI a general "run any Python" tool. The gateway test showed run_python works, so it is technically possible. But if the AI can write arbitrary code, the mistakes we most want to prevent (wrong dimension order, guessed indicator codes) come back. Tool ⑧ is a fixed program that only accepts a verified sheet. A general executor is planned for phase 3, for data transformations.

5The hard step: from plain words to an indicator code

Principle: the database's own indicator list is the sole source of truth. Every database can return a complete "code + description" list through get_dimension_values(db, indicator_dimension) (in WEO that dimension is called INDICATOR; other databases may name it differently, so tool ② finds it first). The list is stable for a given database, so it is downloaded once and cached locally. That cached list is the foundation. The user's words are fuzzy-matched against it, the top five are shown, and the user confirms. A hand-maintained lookup table exists only as a supplement: it can boost a candidate's score, it can never bypass the list.

Step by step

  1. Get the foundation. Once the database is known, tool ② tells us which dimension is the "indicator" (in WEO it is INDICATOR; in CPI-style databases the "indicator" is really a combination of INDEX_TYPE, COICOP_1999 and TYPE_OF_TRANSFORMATION). Tool ③ then downloads every value of that dimension in one go: code, official description, plus unit and scale from the metadata. It is saved as a local file. The list changes rarely, so a refresh every 3 months is enough, with a manual refresh available.
  2. Build a search phrase. The user's words may be in another language or colloquial. During the parse step the AI turns them into an English search phrase and extracts a few hints: level or rate of change, constant or current prices, local currency or US dollars, percent of GDP or absolute value. The hints are used for ranking.
  3. Score every row in the list. Each row gets a score from three parts: word overlap between phrase and description; string similarity (tolerates spelling and word order); and matches after abbreviation expansion using a very small fixed table (GDP, CPI, pct, yoy and the like, separate from the lookup table). If the user typed a code directly (e.g. NGDP_RPCH), an exact code match takes the top score.
  4. Boost from the lookup table. If the search phrase matches an entry in the hand-maintained table, that code gets a fixed bonus so it is more likely to reach the top five and the first place. It must still be in the list and still be confirmed by the user. On every load the table is checked against the list; entries pointing at codes that do not exist are flagged.
  5. Show the top five. Each row shows code, official description and unit; the best is pre-selected; the user confirms with one click or picks another. If none fit, the user rephrases, or the AI suggests a different database. The final choice is written to the sheet together with the "words → code" pair.
  6. Feed the lookup table. Logged "words → code" pairs accumulate in a review file. The team reviews it periodically and promotes stable, frequent pairs into the table. The table grows from real use; it does not need to be complete on day one.

Design choices

  • Confirm every time? Yes in v1, but as a single click. Confirmation is already step 4 of the lifecycle, so the indicator candidates appear on the same screen as the whole sheet; no extra round of dialogue. Once the lookup table has grown and the top-1 accuracy is high enough, "auto-accept when the first candidate is far ahead of the second" can be considered.
  • What does the AI do in this step? Two light things only: turn the user's words into a search phrase, and optionally re-rank the top 15 by reading their descriptions against the hints. It does not generate codes and does not make the final decision. Scoring is ordinary code and can be tested offline.
  • Several indicators in one request. Each indicator phrase goes through matching and confirmation separately ("GDP growth" and "inflation" each need their own code), but they end up in the same sheet and the same query: imf_datatools joins several values of one dimension with +, e.g. USA+JPN.NGDP_RPCH+PCPIPCH.A. One download, one file, not one query per indicator.
  • Semantic (embedding) search later? Not yet. The list is a few hundred rows; word matching plus the abbreviation table plus the lookup table will most likely be enough. If the test cases reveal a set of phrasings that word matching cannot handle, embeddings can be added as one more score term. The list stays the foundation either way.

Countries and time

  • Countries use the same method: the list comes from get_dimension_values(db, 'COUNTRY'), and names are far easier to match than indicators. Country groups ("advanced economies", "G20") are expanded with tool ④, never recited by the AI.
  • Time uses the package's own formats (2020, 2020Q2, 2020-05). Phrases like "the last ten years" are converted by the AI against today's date. Frequency is a dimension like any other: if the database offers several and the user did not say, the agent asks rather than defaulting to annual.

6Code generation and execution

Once the sheet is resolved, the three language versions are a template fill, with no AI involved. imf_datatools uses the same query syntax in all three languages, so the only differences are each language's boilerplate. Here is one sheet rendered three ways.

Python (this is the one the agent runs)

from imf_datatools import idata_utilities
idata_utilities.PRIVATE = True

db  = 'IMF.RES.WEO:WEO_LIVE'
key = 'USA+JPN.NGDP_RPCH.A'   # COUNTRY.INDICATOR.FREQUENCY
df  = idata_utilities.get_idata_data(
        db, key=key, start='2015', end='2026',
        longformat=True)
df.to_csv(r'C:\Users\<you>\Downloads\WEO_LIVE_....csv')

Stata

idatause private
idatause data, ///
    database(IMF.RES.WEO:WEO_LIVE) ///
    query(USA+JPN.NGDP_RPCH.A) ///
    tin(2015, 2026) panel(COUNTRY) clear
export delimited using ///
    "C:\Users\<you>\Downloads\WEO_LIVE_....csv", replace

R

library(reticulate)
use_python("C:/ProgramData/Python3", required = TRUE)
Sys.setenv(TZ = "UTC")
imf_datatools <- import("imf_datatools")
imf_datatools$idata_utilities$PRIVATE <- TRUE
df <- imf_datatools$get_idata_data(
  'IMF.RES.WEO:WEO_LIVE', 'USA+JPN.NGDP_RPCH.A',
  start = '2015', end = '2026', longformat = TRUE)
write.csv(df, "C:/Users/<you>/Downloads/WEO_LIVE_....csv")

Three points about execution

  • Only Python runs, whichever language the user chose to view. Stata and R code is for copying. The agent's machine needs neither Stata nor R, and there is one execution path to harden.
  • It runs in a separate process. The first access to internal data opens a browser tab for sign-in and blocks until the user finishes. In a separate process the interface stays responsive and can show "waiting for IMF sign-in". The session expires after an hour; the program translates that error into "please sign in again". IMF Windows machines have no bash, so the company Python interpreter is started directly, with no shell.
  • The file goes to Downloads. The file name is derived from the sheet. A sidecar .json with the sheet and the retrieval trace is saved beside it, so a file found later can be traced and re-run.

7What changed from the first sketch

The original idea (identify fields → look up indicator codes → generate code in three languages → execute via tools → save to Downloads) is kept in full. These are the changes this design makes on top of it.

  1. Four fixed fields become "ask the database for its dimensions". See section 2.
  2. The AI fills the sheet; templates write the code. A template cannot drop a dot from the key or forget PRIVATE = True. The three languages come for free and can be verified with ordinary tests. Letting the AI write code directly would make three languages three chances to be wrong.
  3. Only Python is executed. See section 6.
  4. The step order is enforced by code. If the sheet is not fully resolved, tool ⑧ refuses and tells the AI what is missing. We do not rely on the prompt alone.
  5. Indicator lookup is fuzzy matching on the database's own list, top five confirmed by the user, rather than a single keyword search. The lookup table only boosts; it never bypasses the list. See section 5.
  6. A confirmation step before execution. One extra click prevents the most expensive failure: a file that looks right but was the wrong query.
  7. Every session leaves a record. The retrieval path shown to the user is also the source of test cases, and confirmed indicator picks feed the lookup table.

How this connects to the team discussion

  • Swappable interface: there is a single channel between the interface and the AI brain (messages in, events out). Streamlit for the prototype; moving to a desktop window later means rewriting only the interface layer. Streamlit's rerun-the-whole-script behaviour is contained in that layer, so AI and tool calls are not repeated.
  • No bash on Windows: execution uses a Python subprocess, no bash needed.
  • Gateway tool calling is confirmed: the code previously shelved in the repo's archive/ folder (tool definitions, dispatcher, test harness) is exactly the starting point for this design and can be reused.

8Decisions for the team

QuestionRecommendation
What if the user does not name a database?Decided: ask the user. Fuzzy-match their answer against the catalogue and confirm the id. Never infer the database from the indicator.
Default output format?Decided: long CSV (one row per observation); add .dta when the user chose Stata. Remember the user's last choice within a session.
Should the agent run Stata or R itself?Not in v1. Revisit only if users report that copied Stata code behaves differently from the Python run.
How to handle the sign-in pop-up in the desktop version?Let the system browser open and show "waiting for sign-in". Embedding the IMF sign-in page in the desktop window would need a security review; not in v1.
Who maintains the lookup table?Engineering owns the file format and the review script; an economist approves new entries from the log periodically.
Write test cases before building?Yes. The team writes 20 plain-language requests with the correct sheet for each. That is the acceptance test.

9Three phases

Phase 1 · Working
  • AI brain, query sheet, connection to the IMF gateway.
  • Nine tools, local indicator-list cache, hand-written lookup table for WEO_LIVE and CPI.
  • Code templates for three languages, Python execution, save to Downloads.
  • Streamlit interface; 20 test cases. The tool-calling loop and idata_fetch are built by the harness owner and merged against the contract in idata_agent/handoff/README.md.
  • Acceptance: all 20 cases produce the correct sheet, and a real run on an IMF machine produces files for WEO_LIVE and CPI.
Phase 2 · Desktop
  • pywebview desktop window; settings for output folder and default language.
  • Indicator-list cache on a shared drive so everyone uses the same snapshot; lookup-table review workflow.
  • Multi-turn sessions: "now the same for Korea", "and add CPI".
Phase 3 · Beyond retrieval
  • Let the AI write data-processing code (growth rates, frequency conversion, merges), with the same confirm-before-run rule.
  • Other datatools sources (Haver, DMXe, World Bank).

AGlossary

Language model (LLM)
Models such as GPT or Claude. Called "the AI brain" in this document.
Tool call
The model does not act directly. It says "please call this function with these arguments"; the program runs it and returns the result; the model decides the next step.
Query sheet (QuerySpec)
The table in section 2. In code it is a structured object that goes from draft to confirmed and runs through the whole flow.
Template
A piece of code with blanks. The program fills the sheet's values into the blanks to get complete code.
Cache
A result fetched once from the network and stored locally, so the next call reads the local copy.
Subprocess
A separate program started to do a job. If it hangs, the main program is not affected.
Streamlit / pywebview
Two ways to build the interface. Streamlit is quick to write and suits a prototype; pywebview is a desktop window showing a web page and suits the real version.
